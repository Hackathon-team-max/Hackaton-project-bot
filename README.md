# 📑 DocFlow — Социальный чат-бот и мини-приложение для студентов

Сервис **DocFlow** разработан в рамках хакатона (Команда №82) и представляет собой интегрированное решение на платформе **«Макс»**, предназначенное для автоматизации и упрощения процесса сбора и верификации документов студентов при поступлении в высшие учебные заведения (на примере МГТУ им. Н.Э. Баумана).

---

## 🎯 1. Назначение решения

Проект решает проблему сложной, непрозрачной и бюрократизированной процедуры подачи документов в университеты. **DocFlow** агрегирует требования вузов, предоставляет пользователю интерактивный чеклист готовности документов, интегрируется с государственными сервисами (Госуслуги) для быстрого заполнения анкет и минимизирует ручную проверку со стороны приемной комиссии.

---

## 👥 2. Основной пользовательский сценарий

1. **Инициализация в чате (Двустороннее общение бэкенда и МАКС):** Абитуриент пишет стартовую команду в чат-бот на платформе «Макс». C++ бэкенд, постоянно опрашивающий API платформы, мгновенно перехватывает это событие, отправляет обратно текстовое приветствие с меню и генерирует инлайн-кнопку запуска мини-приложения (`type: "open_app"`).
2. **Переход в Web App:** Студент нажимает на кнопку в чате. Безопасный мост платформы МАКС открывает встроенное React-приложение, передавая ему подтвержденный `user_id`.
3. **Заполнение профиля:** В интерфейсе Web App студент заполняет личные данные (ФИО, СНИЛС, паспортные данные, адрес). Данные безопасно отправляются на бэкенд и сохраняются в базу.
4. **Выбор университета:** Студент выбирает целевой вуз (например, МГТУ им. Баумана). 
5. **Интерактивный чеклист справок:** Сервер динамически отдает структурированный список документов, разделенный на две категории: **Обязательные** (паспорт, аттестат, СНИЛС) и **Дополнительные** (справка СЭМД-196, приписное свидетельство, квоты по инвалидности). Каждая позиция снабжена прямой ссылкой на соответствующий сервис Госуслуг для оперативного получения.
6. **Контроль и сдача:** Приложение отслеживает готовность пакета документов, формируя прозрачный статус для абитуриента.

## 🏗️ 3. Состав и архитектура решения

Проект построен по модульной многослойной архитектуре с двусторонним асинхронным взаимодействием:

```text
         ┌────────────────────────────────────────────────────────┐
         │                     Платформа МАКС                     │
         └─────────────┬────────────────────────────▲─────────────┘
                       │                            │ 
                       │ (MAX WebApp Bridge / API)  │ (Асинхронный Long Polling / libcurl)
                       ▼                            │
  ┌──────────────────────────────────────────┐      │
  │                 ФРОНТЕНД                 │      │
  │  React 18 + Vite + TS (HashRouter)       │      │
  └────────────────────┬─────────────────────┘      │
                       │                            │
                       │ (REST HTTP JSON API)       │
                       ▼                            │
  ┌─────────────────────────────────────────────────┴─────────────┐
  │                             БЭКЕНД                            │
  │  C++17 Сервер: httplib (REST) + startLongPolling() (Бот)       │
  └────────────────────┬──────────────────────────────────────────┘
                       │ (SQLite C API Wrapper)
                       ▼
  ┌───────────────────────────────────────────────────────────────┐
  │                        БАЗА ДАННЫХ (DAL)                      │
  │  SQLite3 (Локальный отказоустойчивый файл, индекс "order")    │
  └───────────────────────────────────────────────────────────────┘
```

* **Frontend (React/Vite/TS):** Одностраничное приложение (SPA). Слой репозиториев инкапсулирует логику получения данных, переключаясь между `Production` (реальные HTTP-запросы) и `Preview` (локальное хранилище `localStorage` для автономной демонстрации).
* **Backend (C++17):** Совмещает в себе два независимых параллельных контура:
  1. **REST API сетевой слой:** обрабатывает HTTP-запросы от фронтенда через `httplib` с пулом рабочих потоков. Защищен `std::mutex` для потокобезопасного доступа к СУБД.
  2. **Модуль Long Polling (`startLongPolling`):** работает в основном потоке приложения, используя `libcurl` для непрерывного удержания соединения с серверами платформы «Макс». Он асинхронно слушает входящие сообщения от пользователей в чате и мгновенно отправляет ответные команды управления.
* **Database Layer (C++ / SQLite):** Слой абстракции данных (DAL). Реализует подготовленные выражения (`Prepared Statements`), транзакционность при создании таблиц и автоматическую валидацию соответствия схемы БД при старте приложения.

## 🐋 4. Быстрый запуск (Docker-compose)

Запуск всей инфраструктуры проекта (скомпилированный C++ бэкенд, непрерывный Long Polling процесс бота, база данных, настроенный Nginx-прокси и собранная статика React фронтенда) выполняется **одной командой** из корня репозитория:

```sh
docker-compose up --build -d
```

## ⚙️ 5. Параметры окружения и порты

### Переменные окружения (.env)

| Переменная | Контур | Обязательный | Назначение | Пример |
| --- | --- | --- | --- | --- |
| `BOT_TOKEN` | Backend | **Да** | Секретный токен авторизации бота в сети МАКС для Long Polling | `123456:ABC-DEF...` |
| `PORT` | Backend | Нет | Внутренний порт C++ сервера (по умолчанию `8080`) | `8080` |
| `BACKEND_URL` | Frontend | Нет | Внешний URL бэкенда для CORS-запросов фронта | `https://example.com` |

### Сетевые порты
* **`80` (HTTP) / `443` (HTTPS):** Внешние публичные порты Nginx для доступа пользователей к Web App и REST API.
* **`8080`:** Внутренний изолированный порт C++ сервера (скрыт за прокси, доступен внутри Docker-сети).

## 📦 6. Зависимости и интеграции

### Технологический стек и файлы зависимостей:
* **Backend:** C++17, `libcurl` (асинхронный транспорт для удержания Long Polling канала связи с МАКС), `SQLite3` (хранилище), `nlohmann/json` (сериализация). Зависимости сборки фиксируются в `server/CMakeLists.txt`.
* **Frontend:** Node.js 22, React 18, Vite. Зависимости и версии библиотек жестко зафиксированы в файле `frontend/package-lock.json`.
* **Тестирование:** Python 3, `jsonschema`, `pyyaml`. Зафиксировано в `requirements.txt`.

### Внешние интеграции:
1. **API Платформы МАКС:** Двусторонний асинхронный обмен сообщениями и событиями команд через механизмы Long Polling.
2. **Портал Госуслуг:** Внешние бесшовные ссылки на целевые регламентированные формы получения документов воинского учета, медицинских карт СЭМД-196 и подтверждения инвалидности.

## 💾 7. Работа с данными и тестовые сценарии

### Описание структуры БД:
Данные хранятся в файле `application.db`. Схема включает:
* Таблицу `users` с автоматическим трекингом даты изменения (`updated_at` в ISO 8601). Поля ФИО хранятся раздельно по правилам нормализации СУБД, а метод `User::fullName()` динамически склеивает их при выдаче.
* Таблицу `documents` с жестким ограничением типов (`CHECK` на категории `mandatory`/`additional`).
* Индекс `(university_id, category, "order", id)`, гарантирующий выборку документов вуза СУБД SQLite в **идеально отсортированном виде** на уровне ядра базы данных.

### Порядок работы с тестовыми данными (Seed):
В проект встроен механизм **автоматического сидинга**. При первом запуске сервера с пустой базой данных система автоматически считывает требования со скриншота Госуслуг и наполняет SQLite 9-ю эталонными документами для вуза `"bmstu"` с жестко выставленными приоритетами `order`.

## 🧪 8. Пошаговый сценарий проверки роботом-валидатором

В корне репозитория развернут эталонный комплект автоматического контроля качества API в соответствии со спецификацией **DATA-API 1.0**:

1. На сервере автоматической проверки жюри запускается скрипт-валидатор, сопоставляющий сценарии тестов с официальным контрактом путей:
   ```bash
   python validate_data_api.py DATA-API.yaml --openapi ./openapi.yaml
   ```
2. **Сценарий `DATA-API.yaml` выполняет следующие автоматические шаги:**
   * **`health`:** Отправляет `GET /api/ping`. Ожидает `200 OK` и строгое совпадение JSON-схемы ответа `{"ok": true}`.
   * **`upsert-user-profile`:** Отправляет `POST /api/user/profile` с динамической переменной тестового пользователя платформы `"${userId}"`. Ожидает успешную запись. Метод `extract` перехватывает сгенерированный ID в переменную `savedUserId`.
   * **`read-user-profile`:** Динамически вызывает `GET /api/user/{userId}`, подставляя из памяти `savedUserId`. Жестко сверяет структуру всех 8 полей ответа из SQLite (`exists`, `passport`, `snils` и т.д.).
   * **`get-university-documents`:** Запрашивает `GET /api/universities/bmstu/documents`. Проверяет корректность выдачи массивов `mandatory` и `additional` и их сортировку.

## 🛑 9. Известные ограничения MVP и остановка

### Ограничения:
* В соответствии с техническим заданием бота, удаление профиля пользователя из интерфейса Web App не предусмотрено. В связи с этим в блоке тестов `cleanup` метод удаления эмулируется безопасным занулением полей (`POST` пустой структуры поверх созданного ID), что предотвращает загрязнение дискового пространства и сохраняет идемпотентность API.

### Порядок остановки и перезапуска:
* Для полной остановки контейнеров и сохранения состояния базы данных в файле:
  ```sh
  docker-compose down
  ```
* Для полной очистки контейнеров, кэша сборки фронтенда и сброса базы данных к начальному состоянию сидинга:
  ```sh
  docker-compose down -v
  ```
